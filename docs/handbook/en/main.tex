\section*{Executive Report}
\addcontentsline{toc}{section}{Executive Report}
The repository implements a sentiment-analysis product with two tightly coupled planes. The online plane is an Angular frontend served by Nginx, a FastAPI backend in \texttt{src/main.py}, and an in-process inference engine centered on \texttt{src/model/baseline.py}. The offline plane is an ML artifact pipeline defined by \texttt{dvc.yaml}, \texttt{params.yaml}, \texttt{src/data/}, \texttt{src/training/}, and \texttt{src/scripts/}. The online plane consumes artifacts produced by the offline plane rather than training models at request time.

The strongest implementation evidence is end-to-end completeness. The repository contains real prediction endpoints, real explainability, synchronous CSV batch processing, DVC-driven data and training stages, ONNX export, Prometheus metrics, Grafana provisioning, MLflow integration, and an automated test suite across contracts, data, model, scripts, and training. The weakest areas are enterprise hardening and operational durability. Authentication is absent. Authorization is absent. \texttt{/batch\_status/\{job\_id\}} is mocked. Evaluation status is process-memory only. The backend is a single process that owns HTTP serving, model loading, SHAP, ABSA, and batch inference.

The system is best classified as a \textbf{hybrid architecture: modular monolith runtime plus embedded ML platform}. It is not a microservice system. The serving layer is one FastAPI deployable. The frontend, Prometheus, Grafana, and MLflow are separate containers, but they do not own domain-specific service boundaries. The ML platform is repository-local and script-driven rather than service-oriented.

\section{Section 1 - Executive Technical Summary}

The system converts free-form text into structured sentiment outputs for interactive use and CSV batch use. It also demonstrates the full AI application lifecycle: data download, preprocessing, validation, finetuning, evaluation, ONNX export, runtime loading, prediction, explanation, and monitoring.

\subsection{Technical Maturity Assessment}
The repository exceeds a toy prototype because it includes a functioning UI, an explicit API contract layer, a concrete inference abstraction, training and export automation, test coverage, and infrastructure manifests. It does not reach enterprise production maturity because trust boundaries, persistent job state, secure secret handling, and workload isolation are missing.

\subsection{System Classification}
\textbf{Classification: Hybrid Architecture.}

Justification:
\begin{itemize}[leftmargin=1.2em]
  \item the request-serving backend is one FastAPI monolith with one global model instance
  \item the frontend is a separate Angular/Nginx container, but not an independently versioned domain service
  \item monitoring services are support services rather than business services
  \item the repository embeds a full ML artifact pipeline with DVC and MLflow
\end{itemize}

\section{Section 6 - Backend Analysis}
\subsection{FastAPI Architecture}
The backend is a single FastAPI application with a global model singleton and request middleware. The app lifecycle is startup-heavy because model loading and ABSA preload happen in the lifespan function. There is no service layer split separate from route handlers; routing, response shaping, and metrics observation remain in \texttt{src/main.py}.

\subsection{Routing and Dependency Injection}
\begin{itemize}[leftmargin=1.2em]
  \item dependency: \texttt{get\_model()} returns the global \texttt{ml\_model} or raises HTTP 503
  \item helper: \texttt{resolve\_request\_language()} returns explicit \texttt{lang} if provided, else uses \texttt{LanguageDetector}
  \item middleware: CORS plus Prometheus middleware from \texttt{src/monitoring/metrics.py}
  \item exception handlers: \texttt{UnsupportedLanguageError} mapped to HTTP 400 and \texttt{ModelError} mapped to HTTP 500 as \texttt{text/plain}
\end{itemize}

\subsection{Validation and Contracts}
Validation is primarily schema-driven in \texttt{contracts/schemas.py}. \texttt{PredictRequest} enforces text length 1 to 2000. \texttt{ExplainResponse} validates that \texttt{tokens} and \texttt{shap\_values} lengths match. Batch CSV validation is route-local and checks parseability and presence of a \texttt{text} column.

\subsection{Backend Control Flow}
\begin{mermaidblock}
flowchart LR
  Request --> CORS
  CORS --> Monitor[monitor_middleware]
  Monitor --> Route[src/main.py routes]
  Route --> Dependency[get_model()]
  Route --> Lang[resolve_request_language]
  Route --> Model[BaselineModelInference]
  Route --> Schema[Pydantic response models]
  Schema --> Response
\end{mermaidblock}

\subsection{Background Tasks and Long-running Work}
\begin{itemize}[leftmargin=1.2em]
  \item batch inference is not a FastAPI background task; it is executed with \texttt{asyncio.to\_thread()} inside the request scope
  \item evaluation uses \texttt{BackgroundTasks.add\_task()} and stores state in module-global \texttt{\_evaluate\_state}
  \item there is no queue, no worker process, and no durable state store
\end{itemize}

\subsection{Metrics Collection}
Middleware records request count and request latency for all paths. The prediction route separately observes model inference latency by normalized language label. There is no metric for batch row count, SHAP latency, ABSA latency, startup duration, or evaluation duration.

\section{Section 13 - Security Analysis}
\subsection{Evidence-based Findings}
\begin{longtable}{@{}p{0.12\textwidth}p{0.26\textwidth}p{0.16\textwidth}p{0.18\textwidth}p{0.20\textwidth}@{}}
\toprule
\textbf{Severity} & \textbf{Finding} & \textbf{Evidence} & \textbf{Impact} & \textbf{Recommendation} \\
\midrule
\endhead
Critical & no authentication or authorization on any route & \texttt{src/main.py} exposes all endpoints without auth dependencies & any reachable client can call prediction, explanation, evaluation, and metrics & add API auth at gateway or app layer before external exposure \\
High & wildcard CORS allows all origins with credentials enabled & \texttt{CORSMiddleware allow\_origins=["*"]} and \texttt{allow\_credentials=True} & broad browser attack surface and poor boundary hygiene & restrict allowed origins and disable credential support unless required \\
High & Grafana default admin password is committed in compose & \texttt{GF\_SECURITY\_ADMIN\_PASSWORD=admin} in \texttt{docker-compose.yml} & trivial dashboard compromise in exposed environments & externalize secret and rotate default admin credentials \\
High & build-time artifact pull requires secrets in image build context & \texttt{Dockerfile} uses DVC pull with DagsHub credentials & secret mishandling risk in local and CI builds & move to secure build secret mechanism or pre-provision artifacts \\
Medium & admin-style evaluation trigger is public & \texttt{POST /evaluate} has no access control & untrusted users can force expensive background evaluation & protect the route or remove from serving deployment \\

\section{Section 14 - Performance Analysis}
\subsection{Observed Architecture Constraints}
The repository includes a benchmark stage for ONNX but the report cannot claim general production timings without executing the workloads. What is implementation-evident is the performance shape:
\begin{itemize}[leftmargin=1.2em]
  \item startup is expensive because the app loads the primary model and preloads the ABSA pipeline in lifespan
  \item \texttt{/predict} performs one sentiment inference plus ABSA plus optional sarcasm logic in one request
  \item \texttt{/explain} is heavier than \texttt{/predict} because it constructs SHAP explanations per request
  \item \texttt{/batch\_predict} skips ABSA to reduce cost, but still performs full sentiment inference and row reconstruction synchronously
  \item the backend remains CPU-sensitive because the compose file explicitly increases thread counts and CPU limits
\end{itemize}

\section{Section 17 - Scalability Analysis}
\subsection{Application Scalability}
The backend can scale only within the limits of in-process model serving. Horizontal scale is possible at the container level, but stateful assumptions remain weakly defined because evaluation state is local to one process and there is no shared queue or job store.

\subsection{Model Scalability}
\begin{itemize}[leftmargin=1.2em]
  \item sentiment scoring scales better in ONNX mode than SHAP and ABSA
  \item sarcasm scoring adds per-text overhead
  \item SHAP does not scale well for high request concurrency in the current design
\end{itemize}

\subsection{Operational Scalability}
\begin{itemize}[leftmargin=1.2em]
  \item local Compose is sufficient for development and demos
  \item there is no orchestration manifest for Kubernetes or rolling replacement
  \item there is no externalized queue, cache, or database for cross-instance coordination
\end{itemize}

\subsection{Primary Bottlenecks}
\begin{itemize}[leftmargin=1.2em]
  \item startup model load time
  \item SHAP request cost
  \item ABSA request cost
  \item synchronous batch route
  \item single backend process owning mixed workloads
\end{itemize}

\section{Section 20 - Final Technical Conclusion}
The repository is a technically meaningful full-stack AI system rather than a partial demo. It contains a real user interface, a real FastAPI contract surface, a functional inference abstraction, a reproducible artifact pipeline, exportable ONNX serving assets, monitoring integration, and broad tests. Those are genuine strengths.

The decisive weaknesses are not missing architecture diagrams or missing concepts; they are missing production controls. The current implementation does not protect endpoints, does not persist long-running job state, uses a mocked batch-status endpoint, colocates heavy analysis with request serving, and exposes support services with weak defaults.

Final verdict: \textbf{strong implementation-first assessment target, suitable for learning, demonstration, and controlled internal use; not yet suitable for open production exposure without security, durability, and workload-isolation remediation.}

\section{Section 22 - Maintainability Analysis}
\subsection{Code organization}
The repository is organized as a two-plane system: online serving under \texttt{src/main.py}, \texttt{src/model/}, \texttt{contracts/}, and \texttt{app/}; offline artifact production under \texttt{src/data/}, \texttt{src/training/}, \texttt{src/scripts/}, \texttt{dvc.yaml}, and \texttt{params.yaml}. This is coherent, but it concentrates important behavior in \texttt{src/main.py} and \texttt{src/model/baseline.py}.

\subsection{Complexity assessment}
\begin{itemize}[leftmargin=1.2em]
  \item \texttt{BaselineModelInference} is the highest-complexity class because it multiplexes baseline HF, finetuned PEFT, ONNX, ABSA, sarcasm, and SHAP behavior
  \item \texttt{src/main.py} is the highest-complexity route file because it owns startup, routing, validation, batch, evaluation, and metrics wiring
  \item \texttt{src/scripts/run\_finetuning.py} is the highest-complexity training entrypoint because it manages data loading, balancing, tokenization, PEFT, trainer construction, and MLflow integration
\end{itemize}

\subsection{Coupling assessment}
The tightest couplings are \texttt{src/main.py} $\leftrightarrow$ \texttt{src/model/baseline.py}, \texttt{app/.../sentiment-analysis.service.ts} $\leftrightarrow$ \texttt{src/main.py}, and \texttt{src/scripts/export\_onnx.py} $\leftrightarrow$ \texttt{src/model/onnx\_exporter.py}. These couplings are intentional, but they mean that interface changes require coordinated edits across backend, frontend, tests, and docs.

\subsection{Separation of concerns}
Separation is good at the repository boundary, weaker inside the runtime boundary. The code separates contracts, data, training, and model modules well, but the runtime service still combines request handling, inference orchestration, batch processing, and evaluation triggers in one deployable.

\subsection{Testability}
Testability is materially better than the average demo repository because there are tests for contracts, data, training, model, scripts, API behavior, and performance. The main testability limitations are global model initialization in \texttt{lifespan()} and the dependence on local artifact paths.

\subsection{Extensibility}
The strongest extension points are \texttt{ModelInference}, \texttt{TaskConfig}, and the DVC stage graph. The weakest extension points are the hardcoded route semantics in \texttt{src/main.py} and the global, process-local evaluation state.

\subsection{Provider selection and quantization}
\texttt{OnnxInferenceSession} selects \texttt{CPUExecutionProvider} by default and conditionally prefers CUDA or CoreML when the device and runtime providers are available. \texttt{OnnxExporter.export\_int8()} uses \texttt{AutoQuantizationConfig.avx512\_vnni(is\_static=False, per\_channel=True)} which is a CPU-oriented optimization and therefore only pays off when the deployment host matches the target instruction set. The operational implication is that inference performance is deployment-hardware-sensitive and should be benchmarked on the target machine rather than assumed from export settings.

\subsection{Model loading}
\texttt{BaselineModelInference.\_load\_model()} is the central runtime switch. In \texttt{onnx} mode it loads one or two ONNX sessions; in \texttt{finetuned} mode it loads the base model plus sentiment and sarcasm adapters; otherwise it loads the baseline HF model. This is the core architectural decision that ties runtime behavior to \texttt{ModelConfig.mode}.

\subsection{Latency and memory analysis}
Startup time is dominated by \texttt{BaselineModelInference.\_load\_model()} and \texttt{preload()}, especially in finetuned and ONNX modes. Inference latency is lowest when \texttt{skip\_absa=True} and SHAP is avoided. ABSA latency is high because each detected aspect triggers another zero-shot forward pass. SHAP latency is high because the explainer constructs a local surrogate explanation over the classification pipeline. Memory pressure rises with model size, tokenizer objects, SHAP explainer state, and concurrent batch requests.
