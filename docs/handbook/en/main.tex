\section{Executive Assessment}
\subsection{Business Purpose}
The product turns unstructured customer feedback into structured operational signals: sentiment, aspect-level sentiment, sarcasm cues, and explanation artifacts. The intended business use is review analysis, service-quality monitoring, support triage, and explainable AI demonstration.

\subsection{Product Purpose}
The repository contains two products sharing one codebase:
\begin{itemize}[leftmargin=1.2em]
  \item an online inference service exposed through Angular and FastAPI
  \item an offline ML system for data preparation, finetuning, evaluation, MLflow tracking, and ONNX packaging
\end{itemize}

\subsection{Technical Purpose}
The system is designed to prove that the team can operate a full ML delivery chain:
\begin{itemize}[leftmargin=1.2em]
  \item DVC-managed data flow
  \item Hugging Face and PEFT training
  \item ONNX runtime serving
  \item Prometheus and Grafana observability
  \item containerized deployment through Docker Compose
\end{itemize}

\subsection{Core Value Proposition}
The main value is not raw model novelty. It is the operational packaging of sentiment inference into a service with explainability, batch processing, monitoring, and artifact lineage.

\subsection{Maturity Assessment}

\subsection{Why it is not production ready}
\begin{itemize}[leftmargin=1.2em]
  \item \texttt{src/main.py} exposes all inference and evaluation endpoints without auth.
  \item \texttt{/batch\_status/\{job\_id\}} returns a mock response and is not backed by a queue or durable store.
  \item the frontend language selector emits a language but \texttt{SentimentAnalysisService.predict()} drops it and only sends \texttt{\{text\}}.
  \item Docker Compose ships Grafana with default admin password \texttt{admin}.
  \item health checks only prove model load, not downstream dependencies such as MLflow, Prometheus scrape health, or artifact integrity.
\end{itemize}

\section{Architecture Deep Dive}
\subsection{Frontend}
\textbf{Responsibilities:} message composition, voice capture, history persistence, explain trigger, batch upload, theme control.\\
\textbf{Dependencies:} Angular, HttpClient, local storage, backend \texttt{/api/*} routes via Nginx.\\
\textbf{Risks:} contract drift, hidden language-selector bug, limited frontend test depth.\\
\textbf{Ownership:} UI/UX Lead primary, Backend Lead secondary for API coupling.

\subsection{Backend}
\textbf{Responsibilities:} startup lifecycle, dependency injection, schema validation, exception mapping, health, metrics, evaluate trigger, batch orchestration.\\
\textbf{Dependencies:} FastAPI, pandas, model interface, monitoring middleware, background tasks.\\
\textbf{Risks:} single-process bottleneck, synchronous expensive paths, no auth, in-memory state.\\
\textbf{Ownership:} Backend Lead primary, Solution Lead secondary.

\subsection{Inference Layer}
\textbf{Responsibilities:} sentiment scoring, sarcasm adapter path, ABSA extraction, SHAP explanation, ONNX session loading, language validation.\\
\textbf{Dependencies:} Hugging Face, PEFT, SHAP, onnxruntime, tokenizer artifacts, exported models.\\
\textbf{Risks:} startup latency, SHAP cost, ABSA latency, artifact mismatch, HF model download dependence.\\
\textbf{Ownership:} AI Lead primary, ML Lead secondary.

\subsection{Training Layer}
\textbf{Responsibilities:} dataset loading, deduplication, split strategy, imbalance handling, LoRA config, trainer setup, MLflow logging.\\
\textbf{Dependencies:} Datasets, Transformers, PEFT, sklearn, task configs, params.\\
\textbf{Risks:} data skew, limited reproducibility outside configured data files, implicit dependence on raw file availability.\\
\textbf{Ownership:} ML Lead primary, AI Lead secondary.

\subsection{Monitoring Layer}
\textbf{Responsibilities:} request metrics, dashboard provisioning, alert rule definitions.\\
\textbf{Dependencies:} Prometheus, Grafana, middleware instrumentation.\\
\textbf{Risks:} no tracing, limited model-level business metrics, alerts cover only a narrow failure set.\\
\textbf{Ownership:} Solution Lead primary, Backend Lead secondary.

\subsection{Deployment Layer}
\textbf{Responsibilities:} image build, service topology, ports, resource limits, network and mounted storage.\\
\textbf{Dependencies:} Dockerfile, Dockerfile.train, docker-compose, model and data directories.\\
\textbf{Risks:} no orchestration beyond Compose, secret handling through build args, default credentials, no blue/green or rollback automation.\\
\textbf{Ownership:} Solution Lead primary, Backend Lead secondary.

\section{CTO Review}
\subsection{Would I approve production launch?}
No, not for open or enterprise production. I would approve internal demo, teaching use, and a tightly controlled pilot after basic security hardening.

\subsection{Would I approve enterprise customers?}
No. The current security and operational controls are below enterprise minimums.

\subsection{Would I approve scaling?}
Not yet. The architecture can scale conceptually, but the current deployment and control plane are not ready for it.

\subsection{What concerns me most?}
The biggest concern is false confidence: the repository looks production-shaped, but several critical controls are still absent or mocked. That gap is more dangerous than an obviously early-stage system.

\subsection{What investment should happen next?}
Invest first in platform hardening: authentication, rate limiting, artifact governance, and durable batch execution. After that, invest in multilingual correctness and traceable model operations.

\section*{Implementation Discrepancies Appendix}
\addcontentsline{toc}{section}{Implementation Discrepancies Appendix}
\begin{itemize}[leftmargin=1.2em]
  \item README health example says supported languages are only \texttt{["en"]}; \texttt{ModelConfig.supported\_languages} is actually \texttt{("en","vi")}. Operational impact: docs understate backend capability, but frontend does not safely expose it.
  \item README presents batch processing as async job style; implementation of \texttt{/batch\_predict} is synchronous request-response, while \texttt{/batch\_status} is mocked. Operational impact: clients may assume durability and polling behavior that do not exist.
  \item frontend exposes many language choices in \texttt{ChatInputComponent}, but backend only supports \texttt{en} and \texttt{vi}; the service layer also drops explicit language on predict. Operational impact: user-visible multilingual affordance exceeds real supported runtime.
  \item Compose exposes MLflow on host port \texttt{5005} while service-internal tracking uses \texttt{http://mlflow:5000}; params default to \texttt{http://localhost:5000}. Operational impact: local CLI and container runtime use different connection assumptions.
\end{itemize}
