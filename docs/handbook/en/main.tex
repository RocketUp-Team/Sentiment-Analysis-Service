\section{Part 1 - Executive Assessment}
\subsection{Business Problem}
The business problem is converting free-form customer feedback into operationally useful signals fast enough to support product analytics, customer-support triage, service-quality monitoring, and AI demonstration use cases. Manual reading does not scale and does not provide structured outputs.

\subsection{Product Purpose}
The repository delivers:
\begin{itemize}[leftmargin=1.2em]
  \item an end-user chat and batch UI for sentiment analysis
  \item a FastAPI inference service for prediction, explanation, batch scoring, health, metrics, and evaluation trigger flows
  \item an offline ML pipeline for data download, preprocessing, validation, finetuning, evaluation, and ONNX export
\end{itemize}

\subsection{Technical Objective}
The technical objective is to prove a complete ML-in-production chain:
\begin{itemize}[leftmargin=1.2em]
  \item DVC for data-pipeline stage orchestration
  \item MLflow for experiment and evaluation tracking
  \item PEFT/LoRA for finetuned adapters
  \item ONNX Runtime for optimized serving
  \item Prometheus and Grafana for observability
  \item Docker Compose for integrated deployment
\end{itemize}

\subsection{End Users}
\begin{itemize}[leftmargin=1.2em]
  \item product analysts and business stakeholders reviewing sentiment
  \item demo users interacting with chat-style sentiment explanation
  \item engineers operating the backend and training flows
  \item future owners who must maintain runtime and training artifacts
\end{itemize}

\subsection{Value Proposition}
The value is not only prediction accuracy. The stronger proposition is that the system packages inference, batch handling, explainability, monitoring, and artifact lifecycle into one coherent delivery surface.

\subsection{Implementation-based Justification}
\begin{itemize}[leftmargin=1.2em]
  \item \texttt{src/main.py} exposes working inference and evaluation endpoints.
  \item \texttt{src/model/baseline.py} implements real model orchestration, ABSA, SHAP, and ONNX paths.
  \item \texttt{dvc.yaml} encodes a real multi-stage ML pipeline.
  \item \texttt{docker-compose.yml} wires runtime, frontend, Prometheus, Grafana, MLflow, and training profile.
  \item \texttt{/batch\_status/\{job\_id\}} is mocked, so durable async batch processing is \textbf{Not Implemented}.
  \item authentication and authorization are \textbf{Not Implemented}.
\end{itemize}

\subsection{Plain-language Explanation}
For business stakeholders, the system reads text and returns sentiment plus supporting detail. For engineers, the system is a frontend plus a backend plus an embedded model runtime plus an offline training toolchain. For new team members, the easiest mental model is this: \texttt{app/} is the user surface, \texttt{src/main.py} is the runtime entrypoint, \texttt{src/model/} is the inference core, \texttt{src/data/} and \texttt{src/training/} are the artifact factory, and \texttt{infra/} plus \texttt{docker-compose.yml} are the operating shell around all of it.

\section{Part 6 - Execution Trace}
\subsection{Application Startup}
\begin{enumerate}[leftmargin=1.4em]
  \item Uvicorn imports \texttt{src.main:app}.
  \item FastAPI registers middleware, routes, and exception handlers.
  \item lifespan handler reads environment variable \texttt{MODEL\_MODE}; default is \texttt{onnx}.
  \item \texttt{ModelConfig(mode=mode)} is created.
  \item \texttt{BaselineModelInference(config)} is instantiated.
  \item \texttt{BaselineModelInference.\_load\_model()} loads either ONNX sessions or Hugging Face/PEFT model state.
  \item \texttt{preload()} eagerly loads the ABSA pipeline.
\end{enumerate}

\subsection{Health Check}
\begin{itemize}[leftmargin=1.2em]
  \item File: \texttt{src/main.py}
  \item Function: \texttt{health\_check()}
  \item Input: HTTP GET
  \item Output: \texttt{HealthResponse}
  \item Exception path: dependency raises 503 if global model is not ready
  \item Owner: Backend
\end{itemize}

\subsection{Predict}
\begin{itemize}[leftmargin=1.2em]
  \item File: \texttt{src/main.py}
  \item Functions: \texttt{predict()}, \texttt{resolve\_request\_language()}
  \item Core model function: \texttt{BaselineModelInference.predict\_single()}
  \item Input: \texttt{PredictRequest(text, lang)}
  \item Output: \texttt{PredictResponse}
  \item Exception path: 400 on unsupported language, 500 on model failure
  \item Owner: Backend + AI
\end{itemize}

\subsection{Explain}
\begin{itemize}[leftmargin=1.2em]
  \item File: \texttt{src/main.py}
  \item Function: \texttt{explain()}
  \item Core model function: \texttt{get\_shap\_explanation()}
  \item Input: \texttt{ExplainRequest}
  \item Output: token list, SHAP values, base value, latency
  \item Exception path: model error, tokenizer absence, SHAP runtime error
  \item Owner: Backend + AI
\end{itemize}

\subsection{Batch Predict}
\begin{itemize}[leftmargin=1.2em]
  \item File: \texttt{src/main.py}
  \item Function: \texttt{batch\_predict()}
  \item Input: multipart CSV upload
  \item Output: synchronous \texttt{BatchPredictResponse}
  \item Notes: row cap 500; empty rows converted to failed results; ABSA skipped for performance
  \item Exception path: invalid CSV, missing \texttt{text} column, model batch failure
  \item Owner: Backend
\end{itemize}

\subsection{Evaluation}
\begin{itemize}[leftmargin=1.2em]
  \item Runtime trigger file: \texttt{src/main.py}
  \item Background imports: \texttt{src/model/evaluate.py}
  \item Input: POST no body
  \item Output: immediate started status and separate in-memory status endpoint
  \item Gap: persistent job tracking is \textbf{Not Implemented}
  \item Owner: Backend + ML
\end{itemize}

\subsection{Training}
\begin{itemize}[leftmargin=1.2em]
  \item File: \texttt{src/scripts/run\_finetuning.py}
  \item Main flow: parse args, resolve task config, load raw data, dedup, stratify, oversample, tokenize, build PEFT model, train, evaluate, save adapter, log MLflow
  \item Inputs: task name, raw CSVs, params, environment
  \item Outputs: adapter directory, metrics, MLflow run
  \item Owner: ML
\end{itemize}

\subsection{ONNX Export}
\begin{itemize}[leftmargin=1.2em]
  \item CLI file: \texttt{src/scripts/export\_onnx.py}
  \item Export implementation: \texttt{src/model/onnx\_exporter.py}
  \item Steps: load base model, load adapter, merge, save temp merged model, export FP32 ONNX, quantize to INT8
  \item Outputs: \texttt{models/onnx/*}
  \item Owner: AI
\end{itemize}

\section{Part 7 - Frontend Handbook}
\subsection{Owner}
Nguyen Le Hong Nhi

\subsection{Architecture}
The frontend is an Angular standalone-component application. The key pattern is a thin app shell plus a single service maintaining the message stream.

\subsection{Components}
\begin{itemize}[leftmargin=1.2em]
  \item \texttt{AppComponent}: layout, health polling, history, overlay control, message rendering
  \item \texttt{ChatInputComponent}: text input, language selector, browser speech recognition, send events
  \item \texttt{BatchUploadComponent}: CSV upload, summary cards, results export
  \item \texttt{MessageBubbleComponent}: message rendering and explainability display
\end{itemize}

\subsection{Services and State Flow}
\begin{itemize}[leftmargin=1.2em]
  \item \texttt{SentimentAnalysisService} stores messages in a signal and persists history in local storage.
  \item API calls go to Nginx-relative paths such as \texttt{/api/predict}, \texttt{/api/explain}, and \texttt{/api/batch\_predict}.
  \item health polling runs from the app shell until the backend returns healthy.
\end{itemize}

\subsection{Explainability UI}
Explain is not precomputed in the UI. The service finds the preceding user message for a bot reply and then calls \texttt{/api/explain}. That means explanation depends on chat history order, not on a stable backend-issued prediction id.

\subsection{Batch Upload UI}
Batch upload is modal-driven. CSV selection is local, upload is synchronous, and the result table is rendered in memory. A durable batch-job UX is \textbf{Not Implemented}.

\subsection{Key Risks}
\begin{itemize}[leftmargin=1.2em]
  \item The language selector emits \texttt{lang} but the service drops it on prediction requests.
  \item The UI offers many languages while backend runtime supports only \texttt{en} and \texttt{vi}.
  \item Message history persistence can hide backend readiness by reusing prior chat state.
  \item Automated frontend coverage is limited.
\end{itemize}

\subsection{Extension Points}
\begin{itemize}[leftmargin=1.2em]
  \item wire explicit language end-to-end
  \item add true batch job polling and downloadable artifacts
  \item attach explain requests to prediction ids instead of chat adjacency
  \item split operational settings into authenticated admin surfaces
\end{itemize}

\section{Part 9 - AI Inference Handbook}
\subsection{Owner}
Do Quoc Trung

\subsection{Pipeline}
Input text follows this path:
\begin{center}
Input text $\rightarrow$ language selection $\rightarrow$ tokenization $\rightarrow$ tensors or NumPy arrays $\rightarrow$ logits $\rightarrow$ softmax probabilities $\rightarrow$ label selection $\rightarrow$ optional ABSA and sarcasm $\rightarrow$ optional SHAP
\end{center}

\subsection{Tokenization and Tensors}
\begin{itemize}[leftmargin=1.2em]
  \item HF mode: tokenizer returns PyTorch tensors, truncated at \texttt{max\_length}
  \item ONNX mode: tokenizer returns NumPy arrays for \texttt{onnxruntime}
  \item batching uses padding only when predicting lists of texts
\end{itemize}

\subsection{ONNX Runtime}
\begin{itemize}[leftmargin=1.2em]
  \item provider selection prefers CUDA, then CoreML for MPS, then CPU
  \item sentiment and sarcasm ONNX sessions are loaded separately if available
  \item INT8 path exists through quantized exported models
\end{itemize}

\subsection{Prediction Logic}
\begin{itemize}[leftmargin=1.2em]
  \item sentiment label map is index-based: negative, neutral, positive
  \item sarcasm in finetuned mode uses a dedicated adapter or ONNX session
  \item sarcasm training uses a 3-logit shared-head design while runtime only consumes the first two logits
\end{itemize}

\subsection{ABSA}
ABSA is implemented through a zero-shot classification pipeline, not through a dedicated aspect model trained in-repo. Aspect detection and aspect-sentiment inference each require extra zero-shot passes, which is why batch mode disables ABSA.

\subsection{SHAP}
SHAP is built on demand using a prediction callback and tokenizer. There is no caching, no precomputation, and no request budgeting beyond general route execution time.

\subsection{Language Detection}
Language detection is lightweight and heuristic. It uses Vietnamese diacritic detection and token-count minimums. This is sufficient for a fallback but is not enterprise-grade language identification.

\section{Part 16 - Performance Review}
\subsection{Startup Time}
Exact startup measurements are \textbf{Not Implemented} as committed telemetry. Source analysis shows the dominant costs are model/session loading and ABSA pipeline preload.

\subsection{Memory Usage}
Exact memory profiling is \textbf{Not Implemented}. Likely dominant memory holders are model weights, tokenizer assets, ONNX sessions, and zero-shot model state.

\subsection{CPU Usage}
The runtime is CPU-oriented by default in Dockerfiles. Compose explicitly allocates high CPU limits to the backend. SHAP and ABSA are the most CPU-expensive paths.

\subsection{Inference Latency}
Source and tests indicate:
\begin{itemize}[leftmargin=1.2em]
  \item sentiment-only batch throughput target is at least 100 samples/sec in benchmark tests
  \item full pipeline throughput with ABSA is intentionally much slower
  \item Prometheus alerting considers average inference latency above 500 ms a warning
\end{itemize}

\subsection{Batch Throughput}
Batch predict is synchronous and uses \texttt{asyncio.to\_thread()} for backend responsiveness. It still performs CPU-bound inference in-process. There is no distributed worker model.

\subsection{SHAP Cost}
SHAP is high cost because it builds an explainer on demand and performs repeated model evaluations. This path is suitable for explain-on-demand, not for high-throughput production.

\subsection{ABSA Cost}
ABSA uses zero-shot classification for both aspect detection and sentiment-per-aspect. That makes it accurate enough for a demo architecture but expensive for scale.

\subsection{Scalability Limits}
\begin{itemize}[leftmargin=1.2em]
  \item single backend process owns model state
  \item no horizontal job partitioning
  \item no queue-backed batch workers
  \item no caching for SHAP or aspect extraction
\end{itemize}

  \item README health example lists only \texttt{["en"]}; implementation supports \texttt{en} and \texttt{vi}.
  \item README describes batch processing like an async job; implementation is synchronous request-response and the status endpoint is mocked.
  \item frontend exposes many language options; backend supports only \texttt{en} and \texttt{vi}; frontend prediction requests usually omit explicit \texttt{lang}.
  \item Compose uses internal MLflow URL \texttt{http://mlflow:5000}, host publishes \texttt{5005}, and params default to \texttt{http://localhost:5000}. Local and container assumptions are not unified.
  \item \texttt{contracts/README.md} shows \texttt{/api/v1/*} examples; implementation uses root paths such as \texttt{/predict} and \texttt{/health}, with Nginx adding the frontend-facing \texttt{/api/} prefix.
\end{itemize}
